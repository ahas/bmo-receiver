# receiver

チャットレシーバー `bmo-receiver` は、どのチャットサービスから渡されたメッセージであっても、その行き先を
受け持ちます。ルームとそのメッセージ、ルームごとのルール、権限、ウィンドウを保持し、ルームのエージェントが答える
発言と静かな指示のキューを管理します。ターンを送り出すエンベロープを組み立ててエージェンシーのセッションに渡し、
エージェントの答えをルームへ送り返し、ルームの発言、静かな指示、ジョブの終了が求めるエージェントを起こします。
どのチャットサービスにも基盤ライブラリ `bmo-chat-client` を通じて同じ方法で接続し、それ以外のユニットには
`docs/api.md` と `docs/openapi.json` が定めるとおり HTTP で接続します。

## 構成

| フォルダー | 内容 |
|---|---|
| `src/` | サービス自身のパッケージ: メッセージに対するレシーバーの判断と、それを受け取るウェイク(`receiver/`。ウェイク自体のルール、起こすエージェント、ジョブの質問へのオーナーの回答、休止のゲート、誰の発言を聞くかは `receiver/wake/` の下)、起こされたターンが通るラウンドとその構成要素(`chat/`。会話、ウィンドウ、指示のパス、ルームのブロック、ターンのプロンプト、回答の形、ある人が持つルーム群のスレッド、ターンが書き留めた記録と音声通知の声、静かなルームのタッチ、フォールド、レシーバーが応じるブレインの統合、置き換えられたセッションが残す引き継ぎ、ルームのヘルス、再起動、そして回答を作る指示パイプラインとその段階)、ルームが応答を受け取る経路(`roads/`)、ルームの削除が読むルームの記録(`room_record/`)、イベントストリームとライブボード、それを購読するすべての画面(`events/`。ニュースを強く引き出す呼び出し側のためのリレー専用回線は `events/relay`)、ストア(マイグレーションは `src/store/migration/` の下)とデータルート配下のフォルダー、コンソール、send ツール、`bmo` コマンドが到達するルート(`routes/`)、`bmo` がこのサービスに振り分ける名詞(`command`)、`bmo` コマンドが自身の記録に対して実行する動詞(`verbs/`。ドキュメントが移動したチャットへの再読み込みの通知を含む)、エージェンシーのイベントを聞き、その効果が属する部分へ渡す単一のストリーム(`hearing`)、オーナーのセッションに伝えるワーカーの事実(`workers`)、テキストを切り分ける読み取り(`dashes`、`web_address`、`text`、`form`、`json`、`run_lines`、`rounds`)、メッセージの言葉から読み取る秘密の形と、それを取り除いた保管行(`secrets`)、そしてサービスが起動時に読む設定(`config`)、状態と起動時の処理(`service_start`)、ツールがサービスを見つける場所(`tool_env`)、`src/bin/` の下のサービスのバイナリ |
| `.cargo/` | このワークスペースの Cargo 設定: スイートの実行が守るテストスレッドの上限。各テストの所要時間を、ゲートが監視する制限内に収めます |
| `deploy/` | サービスのユーザーユニット。デプロイがデプロイツリーからリンクし、リポジトリ唯一のサービスとして再起動します |
| `crates/` | `receiver-client`: 固定 API の本体を Rust の型として定義し、ルートごとに呼び出しを 1 つ持ち、そこから生成した OpenAPI ドキュメントと、同じドキュメントから生成した TypeScript パッケージ(`crates/receiver-client/ts/`)を含みます。`receiver-codes`: レシーバーが返すすべての拒否、事実、固定の文言を、構造化されたフィールドを持つコードとして定義します。`receiver-policy`: `policy/` のローダーです。`receiver-ports`: レシーバーが呼び出す各ユニットのトレイトと HTTP クライアントです。`room-calls`: レシーバーの send ツールと、同じ送信を行う `bmo` コマンドが実行中のレシーバーに求めるもので、操作とその引数、誰が求めるか、呼び出しが読むターン、ルームで読む手順、上限内に収まる読み取り、そしてデータルートからレシーバーを見つける場所を含みます。`tool-call`: ツールホストの呼び出しプロトコルのレシーバー側の実装で、このサービスに結び付いたツールが共有します |
| `tools/` | このサービスに結び付いたツール。それぞれ独自の `tool.toml` を持ちます。`send` はエージェントがルームで発言するためのエントリー、`rooms` はエージェントが開き、読み、応答者を指定する、記録だけで存在するエージェントルーム、`wait` は `bmo use` が単独で実行するリマインダーと監視です |

`install.toml`(新しいマシンへのインストールに必要なものの宣言で、`bmo install` が読みます)、`rustfmt.toml`、`CLAUDE.md`、`settings.example.toml`(チェックインされた設定の例で、デプロイ自身のファイルは
データルートの下にあります)、`korean-ledger.json`(コードファイルに残る韓国語の記録で、テストベッドの韓国語

## 個人データ

追跡されるどのファイルにも、メールアドレス、ホームパス、電話番号、トークン、プライベートネットワークのアドレスは
含まれません。`docs/PERSONAL-DATA.md` がルールを定め、テストベッドの `personal-data` チェックが追跡されるすべての
ファイルを読んで確認します。チェックはファイル、行、種類を報告しますが、値は決して報告しません。

## バージョン

- **リポジトリ全体でバージョンは 1 つで、** ワークスペースのものです。`VERSION` がそれを保持し、ワークスペースの
  バージョンはそれと一致します。
- **バージョンはオーナーが宣言したリリースでのみ上がります。** bmo-chat の `docs/conventions.md` 「Versions」が
  定めるとおり、コミット、デプロイ、修正、契約の変更ではバージョンは上がらず、デプロイはコミットで区別します。

## ビルドとテスト

Cargo はテストベッドの Cargo コマンドを通じて実行され、1 つの共有ビルドディレクトリでビルドします。

```sh
bmo-testbed check quick
bmo-testbed cargo check --workspace --all-targets
bmo-testbed cargo test --workspace
bmo-testbed cargo clippy --workspace --all-targets -- -D warnings
cargo fmt --all --check
```

`bmo-testbed check quick` は、何かを実行する前にツリーを読む 4 つのチェックを行います。用語集の用語、コード内の
韓国語、README のフォルダー表、そしてマニフェストが指定する依存関係です。人、エージェント、マシンの名前は
リポジトリ自身のテストがチェックし、このテストは名前の一覧をチェックアウトの外から読みます。テストベッドの
`personal-data` チェックは、追跡されるすべてのファイルからメールアドレス、ホームパス、電話番号、トークン、
プライベートネットワークのアドレスを探します(`docs/PERSONAL-DATA.md`)。

データベースを使うテストは、`BMO_TEST_POSTGRES` が指す PostgreSQL サーバーに自分のデータベースを作ります。この
変数はテストベッドのスイートが設定し、何も指定されていなければマシン自身のソケットを使います。各テストプロセスは
テンプレート `receiver_rs_tmpl_<process>` を 1 つマイグレーションし、各テストにそのコピー
`receiver_rs_copy_<process>_<count>` を渡します。コピーはテストの終了時に削除されます。その際、そのデータベース上の
自ロールのセッションを終了させ、強制せずにデータベースを削除するため、スイートのロールには他のロールのプロセスを
終了させる権限が要りません。コピーが削除されなかったテストは失敗します。プロセスは最初のデータベースを作る前に、
自ロールが所有するテンプレートとコピーのうち、そのプロセスがもうマシン上で動いておらず、どのクライアントの
セッションも接続していないものを削除します。それ以外の名前には触れません。
