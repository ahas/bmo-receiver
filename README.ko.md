# receiver

채팅 수신기 `bmo-receiver`는 어느 채팅 서비스가 메시지를 넘기든 그 메시지가 어떻게 처리되는지를 맡습니다.
방과 메시지, 방마다의 규칙, 권한, 창(window)을 보관하고, 방의 에이전트가 답할 말과 조용한 지시의 대기열을
관리합니다. 턴을 담아 보낼 봉투를 만들어 에이전시의 세션에 넘기고, 에이전트의 답을 방으로 다시 보내며, 방의
말이나 조용한 지시, 작업의 종료가 요구하는 에이전트를 깨웁니다. 모든 채팅 서비스에는 기반 라이브러리
`bmo-chat-client`를 통해 같은 방식으로 닿고, 그 밖의 모든 유닛에는 `docs/api.md`와 `docs/openapi.json`이 정한
대로 HTTP로 닿습니다.

## 구성

| 폴더 | 내용 |
|---|---|
| `src/` | 서비스 자체 패키지: 메시지에 대한 수신기의 판단과 그 메시지를 넘겨받는 깨우기(`receiver/`. 깨우기 자체의 규칙, 깨울 에이전트, 작업의 질문에 대한 소유자의 답, 휴식 게이트, 누구의 말을 듣는지는 `receiver/wake/` 아래), 깨어난 턴이 거치는 라운드와 그 구성 요소(`chat/`. 대화, 창, 지시 단계, 방 블록, 턴의 프롬프트, 답의 형태, 한 사람이 가진 방들의 스레드, 턴이 기록한 내용과 음성 알림의 목소리, 조용한 방의 터치, 접기(fold), 수신기가 응하는 브레인 통합, 교체된 세션이 남기는 인계, 방들의 상태, 재시작, 그리고 답을 만드는 지시 파이프라인과 그 단계들), 방이 응답받는 경로(`roads/`), 방 삭제가 읽는 방의 기록(`room_record/`), 이벤트 스트림과 실시간 보드, 그리고 이를 구독하는 모든 화면(`events/`. 뉴스를 세게 끌어가는 호출자를 위한 릴레이 전용 회선은 `events/relay`), 저장소(마이그레이션은 `src/store/migration/` 아래)와 데이터 루트 아래의 폴더들, 콘솔과 send 도구와 `bmo` 명령이 닿는 라우트(`routes/`), `bmo`가 이 서비스로 보내는 명사(`command`), `bmo` 명령이 자체 기록에 대해 실행하는 동사(`verbs/`. 문서가 옮겨진 채팅에 다시 불러오기를 알리는 일 포함), 에이전시의 이벤트를 듣고 그 효과가 속한 부분으로 넘기는 단일 스트림(`hearing`), 소유자의 세션에 알리는 워커 관련 사실(`workers`), 텍스트를 자르는 데 쓰는 읽기(`dashes`, `web_address`, `text`, `form`, `json`, `run_lines`, `rounds`), 메시지의 말에서 찾아내는 비밀 형태와 그것을 지운 보관 행(`secrets`), 그리고 서비스가 시작할 때 읽는 설정(`config`), 상태와 시작 시의 작업(`service_start`), 도구가 서비스를 찾는 곳(`tool_env`), `src/bin/` 아래의 서비스 바이너리 |
| `.cargo/` | 이 워크스페이스의 Cargo 설정: 스위트 실행이 지키는 테스트 스레드 상한으로, 각 테스트의 소요 시간이 게이트가 감시하는 한도 안에 머물게 합니다 |
| `deploy/` | 서비스의 사용자 유닛. 배포가 배포 트리에서 링크하고 저장소의 유일한 서비스로 재시작합니다 |
| `crates/` | `receiver-client`: 고정 API의 본문을 Rust 타입으로 정의하고 라우트마다 호출 하나를 두며, 이로부터 생성한 OpenAPI 문서와, 같은 문서에서 생성한 TypeScript 패키지(`crates/receiver-client/ts/`)를 담습니다. `receiver-codes`: 수신기가 내는 모든 거부, 사실, 고정 문구를 구조화된 필드가 있는 코드로 정의합니다. `receiver-policy`: `policy/`를 읽는 로더입니다. `receiver-ports`: 수신기가 호출하는 각 유닛의 트레이트와 HTTP 클라이언트입니다. `room-calls`: 수신기의 send 도구와 같은 전송을 하는 `bmo` 명령이 실행 중인 수신기에 요청하는 내용으로, 동작과 그 인자, 누가 요청하는지, 호출이 읽는 턴, 방에서 읽는 절차, 상한 안에 담기는 읽기, 그리고 데이터 루트에서 수신기를 찾는 위치를 담습니다. `tool-call`: 도구 호스트 호출 프로토콜의 수신기 측 구현으로, 이 서비스에 묶인 도구들이 함께 씁니다 |
| `tools/` | 이 서비스에 묶인 도구. 각각 자체 `tool.toml`을 가집니다. `send`는 에이전트가 방에 말할 때 쓰는 진입점, `rooms`는 에이전트가 열고 읽으며 답할 에이전트를 지정하는, 기록만으로 존재하는 에이전트 방, `wait`는 `bmo use`가 스스로 실행하는 리마인더와 감시입니다 |
| `policy/` | 수신기의 고정 수치와 문구. 명령을 맞춰 보는 한국어 낱말도 여기에 포함됩니다 |
| `tests/` | 패키지의 단일 테스트 하네스 `main.rs`: 저장소 전체에 걸친 검사와 파일 하나당 모듈 하나인 서비스 자체 테스트, 그리고 모듈 `tests/integration/`의 통합 테스트. 다른 유닛의 언어로 묻는 테스트 문구는 `tests/fixtures/` 아래에 데이터로 둡니다 |
| `docs/` | 서비스가 하는 일에 대한 정본 문서 |

루트에는 서비스의 패키지이기도 한 Cargo 워크스페이스 매니페스트, `VERSION`의 버전, `testbed.toml`(이 저장소를
테스트하고 검사하고 빌드하고 배포하는 방법에 대한 테스트베드의 선언), `install.toml`(새 머신에 설치할 때 필요한 것으로,
`bmo install`이 읽습니다), `rustfmt.toml`, `CLAUDE.md`,
`settings.example.toml`(설정의 예시로 체크인된 파일이며, 배포 자체의 파일은 데이터 루트 아래에 있습니다),
`korean-ledger.json`(코드 파일에 남은 한국어를 기록하며, 테스트베드의 한국어 검사가 모든 파일을 이에 맞춰
봅니다. 이 저장소의 코드 파일에는 한국어가 없습니다)이 있습니다.

## 개인 정보

추적되는 어떤 파일도 메일 주소, 홈 경로, 전화번호, 토큰, 사설 네트워크 주소를 담지 않습니다.
`docs/PERSONAL-DATA.md`가 규칙을 정하고, 테스트베드의 `personal-data` 검사가 추적되는 모든 파일을 읽어 이를
확인합니다. 검사는 파일, 줄, 종류는 보고하지만 값은 결코 보고하지 않습니다.

## 버전

- **저장소 전체에 버전은 하나이며,** 워크스페이스의 버전입니다. `VERSION`이 이를 담고, 워크스페이스의 버전은
  이와 같습니다.
- **버전은 소유자가 선언한 릴리스에서만 올라갑니다.** bmo-chat의 `docs/conventions.md` 「Versions」가 정한
  대로, 커밋, 배포, 수정, 계약 변경은 버전을 올리지 않으며, 배포는 커밋으로 구별합니다.

## 빌드와 테스트

Cargo는 테스트베드의 Cargo 명령을 통해 실행되며, 이 명령은 하나의 공유 빌드 디렉터리에서 빌드합니다.

```sh
bmo-testbed check quick
bmo-testbed cargo check --workspace --all-targets
bmo-testbed cargo test --workspace
bmo-testbed cargo clippy --workspace --all-targets -- -D warnings
cargo fmt --all --check
```

`bmo-testbed check quick`은 무엇이든 실행하기 전에 트리를 읽는 네 가지 검사를 실행합니다. 용어집의 용어, 코드
속 한국어, README의 폴더 표, 그리고 매니페스트가 지정한 의존성입니다. 사람, 에이전트, 기계가 쓰는 이름은
저장소 자체 테스트가 검사하며, 이 테스트는 이름 목록을 체크아웃 밖에서 읽습니다. 테스트베드의 `personal-data`
검사는 추적되는 모든 파일에서 메일 주소, 홈 경로, 전화번호, 토큰, 사설 네트워크 주소를 찾습니다
(`docs/PERSONAL-DATA.md`).

데이터베이스를 쓰는 테스트는 `BMO_TEST_POSTGRES`가 가리키는 PostgreSQL 서버에 자기 데이터베이스를 만들며, 이
변수는 테스트베드의 스위트가 설정합니다. 아무것도 지정되지 않으면 기계 자체의 소켓을 씁니다. 각 테스트
프로세스는 템플릿 하나 `receiver_rs_tmpl_<process>`를 마이그레이션하고, 각 테스트에 그 사본
`receiver_rs_copy_<process>_<count>`를 주며, 사본은 테스트가 끝나면 삭제됩니다. 이때 그 데이터베이스에 있는 해당
역할 자신의 세션을 끝내고 강제 없이 데이터베이스를 삭제하므로, 스위트의 역할은 다른 역할의 프로세스를 끝낼
권한이 필요 없고, 사본이 삭제되지 않은 테스트는 실패합니다. 프로세스는 첫 데이터베이스를 만들기 전에, 자기
역할이 소유한 템플릿과 사본 가운데 해당 프로세스가 더 이상 기계에서 실행되지 않고 어떤 클라이언트 세션도 붙어
있지 않은 것을 삭제합니다. 그 밖의 이름은 건드리지 않습니다.
